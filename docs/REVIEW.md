原有 55 项自动测试全部通过。新增 14 项检查中，6 项通过，8 项以 `expectedFailure` 保存已确认缺陷。合计 69 项：**61 项通过，8 项待修复的预期失败**。`OK (expected failures=8)` 不等于 69 项全部通过。另有 2 组问题通过实际浏览器复现，未计入自动测试数。

## R1：错误结果持久化凭据

位置：`scope_agent.py:240–262`、`scope_agent.py:335–336`、`scope_agent.py:354–355`。

`ChatClient` 直接把 API Key 拼入 Authorization。密钥含换行时，HTTP 请求头校验会抛出包含该请求头值的 ValueError；`model_run` 原样保存 `str(exc)`，随后 `write_results` 写入 agent.json。UI 分析接口还会返回这份 outcome。

复现使用纯虚构的 `review-only-fake-secret` 加换行，地址仅为回环地址。测试实际生成 agent.json，确认文件包含该虚构密钥。**没有发现正常成功请求也泄露密钥的证据**；触发前提是密钥配置含非法请求头字符。影响在于本地报告可能随后被分享、归档。

建议在创建客户端时拒绝控制字符，并对网络层异常采用固定错误消息；不能依赖一次字符串替换涵盖所有凭据表示。修复后验证 outcome、HTTP 返回及所有导出文件均不含测试密钥。

复现：`python -m unittest test_review.ReviewChecks.test_r1_invalid_header_never_persists_credential -v`。

## R2：异常输入没有形成可恢复的 HTTP 错误

位置：`scope_analysis.py:20–36`、`scope_agent.py:64–65`、`ui_server.py:292`。

两个独立输入都在上传限额内：

- 某个 CSV 数值字段为 140,000 个字符，CSV 解析器抛出 csv.Error，未转换为业务错误。
- 限值最大值为整数 `10 ** 400`，JSON 接受该整数，但 `math.isfinite(value)` 转换时抛出 OverflowError。

HTTP 处理器未捕获这两类异常，结果为连接直接关闭，而不是带 JSON 错误说明的 400。服务进程仍可响应后续请求，不应描述成整个服务器崩溃。

建议在 CSV 解析边界转换 csv.Error；为所有数值入口提供不会抛出 OverflowError 的有限数校验，覆盖限值和选区参数。无需只在最外层吞掉所有异常。

复现：`python -m unittest test_review.ReviewHTTPChecks -v`。

## R3：失败事务破坏记录与证据的一致性

位置：`ui_server.py:71–83`、`ui_server.py:147–183`。

当前注册逻辑先淘汰最老记录，再插入新记录，最后生成报告。已经保存三条记录时，注入 `write_results` 的 OSError，新记录虽然失败，最老记录却已被释放，还留下没有完整报告的新条目。真实上传路径还会清理其临时文件，进一步使该条目失效。

对已有记录重新分析时，代码先重置并改写 session.trace，成功生成压缩包后才替换 archive/outcome。注入写盘失败后，旧压缩包仍保留，但当前 trace 已来自另一轮分析。两项问题均已复现。

建议先用临时分析状态生成完整报告，成功后一次提交 trace、outcome、archive；新记录也应在成功后才进入缓存和执行淘汰。不要靠重新生成旧报告补偿已经删除的原始文件。

复现：`test_review.ReviewChecks` 中两项 `test_r3_*`。

## R4：通道名进入 HTML

位置：`ui/app.js:38–42`、`ui/app.js:57–63`、`ui/app.js:94`。

`shortChannel` 返回的字符串直接进入多处 innerHTML。虽然属性值和其他说明有转义，显示标签本身仍是原始通道名。

在浏览器实际导入以下文件：

```csv
time_s,<b>CH1</b>_V
0,0
1,1
2,0
3,1
```

读取结果确认通道按钮内部生成了真正的 `<b>` 节点，界面显示 CH1，而不是字面名称 `<b>CH1</b>`。截图见 [通道渲染证据](review-channel-rendering.png)。

本轮确认的是 HTML 注入和标签表达错误。现有 CSP 限制了内联脚本和外部资源，**没有证实任意 JavaScript 执行**，不应把现有证据夸大成完整 XSS 利用。

建议使用 textContent 创建标签，或在每个 HTML 文本插值位置调用现有 esc；不要在 shortChannel 内全局转义，因为它也用于 Canvas 文本，需要按输出上下文处理。

## R5：扫描设备会阻塞实时状态接口

位置：`live_stream.py:48–66`、`live_stream.py:184–196`、`devices.py:84`。

`device_request` 持有 LiveMonitor.lock 执行 VISA 枚举和身份查询，status 使用同一把锁。假后端的枚举被事件阻塞时，并发 status 在 200 ms 检查窗口内无法返回，释放扫描事件后才恢复。

当前扫描会拒绝正在运行的监看，因此不是“后台采集过程中一定卡死”。实际问题是扫描期间其他页面的状态、开始及停止请求也等待该锁；枚举没有本项目定义的整体截止时间，慢后端可能延长等待。200 ms 只是本次判定响应性的测试窗口，不是项目承诺的时限。

建议为扫描使用独立的进行中标志，锁内只检查和提交状态，VISA I/O 在锁外执行；同时定义扫描截止与取消策略，仍需保证扫描和新采集不会竞争同一设备。

复现：`test_review.ReviewChecks.test_r5_status_remains_responsive_during_discovery`。

## R6：PNG 头检查不足

位置：`live_stream.py:115–123`。

当前只检查长度、8 字节签名和固定偏移的尺寸。构造一个 24 字节数据，带 PNG 签名以及 1×1 尺寸但缺少完整 IHDR、图像数据和 IEND，仍会发布为正常帧。浏览器无法据此显示完整图像，而后端没有进入错误状态。

建议检查 PNG 的基本分块结构、长度边界和结束块，并处理图片加载失败；按当前需求不必引入重型图像框架。结构检查也不能替代实际解码验收。

复现：`test_review.ReviewChecks.test_r6_truncated_png_is_rejected`。

## R7：关闭 VISA 管理器失败没有归一化

位置：`devices.py:103–104`、`devices.py:116–117`。

`manager.close()` 位于 finally 中，发生的非 ValueError / OSError 异常绕过前面的异常转换。注入 RuntimeError 时直接传播。HTTP 层也没有覆盖这类后端生命周期异常，存在再次断开请求的路径。

建议统一管理关闭异常；保留首个读写错误的含义，关闭失败另作明确诊断。不要因关闭错误掩盖原先的身份读取失败。当前是错误注入证据，没有真实 VISA 后端故障记录。

复现：`test_review.ReviewChecks.test_r7_manager_close_failure_becomes_recoverable_error`。

## R8：会话变化后的界面没有恢复路径

位置：`ui/live.js:114–133`、`ui/live.js:25–35`。

浏览器复现步骤：

1. 页面 A 开始动态演示；页面 B 打开同一工作台并附着该会话。
2. 页面 B 快速停止并重新开始，服务生成新的 stream_id。
3. 页面 A 下一次轮询发现 stream_id 改变，抛错退出轮询，却保留旧的 worker_alive 状态。
4. A 提示“请重新开始”，但开始按钮和数据来源仍禁用；点击停止会因旧 stream_id 被正确拒绝，也不会更新本地状态。刷新才恢复。

实际读取确认 `startEnabled=false`、`sourceEnabled=false`。证据见 [会话恢复问题截图](review-session-recovery.png)。此问题与两个页面切换的时序有关，不是每次慢速停止/启动都会触发。

建议检测会话变化后重新读取权威状态，并提供明确的重新附着或放弃旧会话操作，清除陈旧帧的可冻结状态。**保留后端拒绝旧会话停止新会话的保护**；不能以取消 stream_id 校验来“修复”界面。

## 性能与算法边界

这些数字是当前机器单次探测，不是稳定基准或性能承诺。分析和预览耗时只包含内存数组计算，不包含 CSV 解析、传输、浏览器绘制或模型等待。

| 点数 / 单通道 | analyze_channel | preview_data | 预览点数 |
| ---: | ---: | ---: | ---: |
| 20,000 | 0.0357 s | 0.0059 s | 2,000 |
| 100,000 | 0.0522 s | 0.0051 s | 2,000 |
| 1,000,000 | 0.5647 s | 0.0058 s | 2,002 |

导入分配值得优先优化：29 字节 CSV 的 load_csv 在 tracemalloc 中峰值为 134,226,745 字节，约 128 MiB；本解释器对 `read(128 MiB + 1)` 的分配是主要原因。这是 Python 被跟踪的分配峰值，不是实际物理内存常驻量。可先按文件长度读取到上限，或用有限分块累积；必须保持“哈希与分析使用同一份内容快照”的已有保证。

算法探测确认：1 kHz PWM 在 1%、4%、96%、99% 占空比时，周期、占空比和 FFT 都被保守停用。10%–90% 典型范围的本轮检查通过；5% 和 95% 边界存在百分位插值偏差。原因是 5/95 分位电平不适合稀疏脉冲。这属于当前通用分析能力缺口，不能把“未建立”解释成没有 PWM。建议先独立改进稀疏脉冲候选识别，再验证噪声和误报，不能直接放宽所有阈值。

上一轮“微伏显示成零”的主要问题已有改善：本轮 `1e-6 V` 显示 `1 µV`。仍有极小量级表达限制：`1e-12 V` 显示 `0 µV`、`1e-5 Hz` 显示 `0 Hz`。后者适合用有效数字或科学计数法改进，优先级低于 R1–R5、R8。

模型请求仍在 Workbench 全局锁内执行，图形、报告、导入和冻结会等待模型完成；单次网络等待上限 45 秒，最多六轮，不能把 45 秒当整次分析的上限。实时 frame/start/stop 接口已经绕开此锁，不能沿用旧说法称所有实时请求都被模型阻塞。冻结最多保留五帧，排队过久还可能导致请求中的显示帧过期。
